# ForumMind

> 融合组会制、多智能体辩论与科研 Memory 的“问题—计划—执行—反馈”全链条通用 AI Scientist。

ForumMind 是一个 AI 科研课题组。它由多个具有不同专业视角的 Agent 协作完成资料整理、假设构建、证据审查和实验建议，研究者以课题负责人或 PI 的身份主持过程、查看依据并作出最终判断。

产品总览：[ForumMind 研究工作流](docs/forummind-overall-loop.svg)

## 产品价值

材料科研中的关键问题通常不是缺少一个答案，而是上下文分散在论文、实验表格、聊天记录和个人记忆中，团队很难持续回答：

- 当前课题真正卡在哪里？
- 哪些证据支持某个假设，哪些证据与它冲突？
- 哪些观点已经被质询，哪些风险仍然没有验证？
- 下一步实验为什么值得做？
- 结论改变时，能否回到当时的证据和判断过程？

ForumMind 将这些信息放进同一个课题工作空间，以组会和研究对话为主要交互，让 AI 的价值从“一次性回答”变成“持续协作、持续质询、持续记忆”。

## 适用角色

### 研究者

输入一个模糊的研究方向、实验异常或待解决问题，获得结构化的资料整理、候选假设、证据缺口和可验证的下一步行动。

### PI / 导师

查看竞争性假设、来源、反例、Agent 分歧和实验约束，在关键节点批准、附条件批准、退回、暂缓或终止下一步。

### AI 课题组成员

博士后负责任务澄清、实验约束和阶段建议；博士负责拆解任务、审查产物和组织结论；硕士成员从文献、机制、实验方法和数据等不同视角独立分析。

## 核心工作流

1. **创建课题组**：填写课题名称和研究概述，配置博士后、博士和硕士成员。
2. **建立研究对话**：进入持续存在的课题组聊天，查看成员、组会安排和研究产物。
3. **补充资料**：上传论文、实验记录、表格或其他研究材料，系统保留来源和可定位片段。
4. **澄清任务**：通过 `@` 指定 Agent 或全体成员，Agent 以逐问逐答的方式确认目标、约束、资料范围和交付格式。
5. **启动分析**：任务确认后，在同一聊天流启动 Live 分析，查看进度、工具调用产生的证据和候选结果。
6. **形成竞争性解释**：多个 Agent 独立提出假设、依据、适用边界、反例、预测和可推翻条件。
7. **审查与决策**：博士 Agent 检查证据、边界和缺失观察；PI 审阅候选 Claim 并决定是否批准。
8. **推进实验与结论**：系统根据仍存的分歧生成判别实验建议；研究者执行真实实验，导入结果后更新假设与阶段性结论。
9. **沉淀科研 Memory**：保存研究问题、证据、争点、实验、结果、决策和结论变化，下一次组会从已有认知继续。

## 如何启动

ForumMind 由 Web 前端和 FastAPI 后端组成。首次运行需要 Node.js、pnpm 11.7.0、Python 3.11 及以上版本和 uv。

### 安装依赖

在项目根目录执行：

```powershell
pnpm install
uv sync --directory apps/api
```

### 启动后端

在第一个 PowerShell 窗口执行：

```powershell
$env:CORS_ORIGINS = "http://localhost:3000"
pnpm dev:api
```

后端默认地址为 `http://localhost:8000`。后端启动后，浏览器可以通过 `http://localhost:8000/health` 查看服务是否可用。

### 启动前端

在第二个 PowerShell 窗口执行：

```powershell
$env:NEXT_PUBLIC_API_BASE_URL = "http://localhost:8000"
pnpm dev:web
```

然后打开 `http://localhost:3000` 进入 ForumMind。关闭终端会停止对应服务；再次启动时需要重新设置当前终端中的环境变量。

### 配置模型服务

当前研究聊天使用 Live 分析。进入 Web 界面的“设置”，填写一个 OpenAI-compatible 服务：

- **Provider**：`openai-compatible`
- **Base URL**：例如 Qwen 的 `https://dashscope.aliyuncs.com/compatible-mode/v1`
- **Model**：例如 `qwen-plus`
- **API Key**：对应服务商提供的密钥

也可以使用兼容 OpenAI API 的其他服务。密钥只在后端进程内使用，不要写入源码、聊天消息或提交到仓库。模型服务未配置时可以打开产品和浏览历史内容，但不能完成新的 Live 分析。

## 如何完成一次完整科研流程

### 1. 创建课题组

进入“课题组”并创建新的课题，填写清晰的课题名称、研究概述和资料可信空间。材料科研场景可以先选择脱敏真实资料空间，避免在演示或协作中直接暴露敏感实验信息。

### 2. 配置成员

根据课题需要配置博士后、博士和硕士成员，并为每位成员指定主要能力。例如，让一名成员负责文献与机制分析，让另一名成员负责实验与测试方法，再由数据方向成员检查数据和证据边界。成员的职责应互补，不要让所有成员只重复同一种判断。

### 3. 上传研究资料

在课题组聊天中上传论文、实验记录、CSV/XLSX 数据或其他允许的材料。资料解析后会保留文档、位置和片段标识，后续引用可以回到原始内容。涉及实验数据时，先检查样品编号、单位、字段含义和数据可信等级。

### 4. 通过 `@` 澄清研究任务

在聊天中 `@` 指定成员，说明希望解决的现象、已有观察、约束条件和交付形式。例如：

> @实验约束成员 请分析密度变化与 28 天抗压强度的关系，区分相关性和可能的机制解释，并为下一次组会准备两个可区分的实验方案。

成员会逐轮提出澄清问题。研究者需要回答研究对象、变量、资料范围、时间或资源约束，以及希望得到的结果形式。任务确认完成后，聊天中会出现“开始分析”入口。

### 5. 启动分析并审阅候选结果

点击“开始分析”后，Live 运行会在同一条聊天流中展示分析进度、成员观点、工具产生的证据和候选 Claim。审阅时重点查看：

- 候选 Claim 是否能被清楚地检验；
- 引用是否包含正确的文档、位置和 `chunk_id`；
- 结论是否说明了适用范围、反例、不确定性和可推翻条件；
- 是否把相关性、模型推断或单次观察误写成因果结论。

候选结果可以批准或拒绝。批准表示研究者接受它进入课题记录，并不表示科学验证已经完成；拒绝结果和理由仍会保留，方便下一轮组会追溯。

### 6. 设计、执行并回写实验

根据尚未解决的分歧选择最小判别实验。研究者在真实环境中完成样品制备、养护、测试和表征，再把结果导入实验数据工作区。导入 CSV/XLSX 后先预览字段和单位，再确认生成一个不可变数据版本；后续分析都关联到具体版本。

完成摘要、相关性或分组均值分析后，可以从结果回到源数据的行、列和版本，确认分析依据。最后把实际结果、偏差、失败原因和新的判断写回课题组聊天或 Research Memory，进入下一轮假设审查。

## 如何设计实验

ForumMind 适合把“想验证一个想法”整理成可区分假设的实验计划。实验方案应由研究者审核并执行，AI 负责帮助拆解变量、暴露混杂因素、比较预测和整理数据。

### 先定义问题和竞争性假设

把问题写成可测量的形式，例如“在相同养护条件下，密度变化是否会改变泡沫混凝土的 28 天抗压强度”。至少写出两个能够互相区分的假设：

- **假设 A**：强度变化主要由密度变化引起；
- **假设 B**：观察到的强度变化主要由孔结构、含水状态或养护差异引起，密度只是伴随变化。

每个假设都要写出预测、适用范围、可能的反例和可推翻条件。这样实验的目标是区分解释，而不是只寻找支持当前偏好的数据。

### 明确变量、对照和混杂因素

在方案中分别列出：

- **自变量**：研究者主动改变的因素，例如目标密度或泥浆掺量；
- **因变量**：实际测量的结果，例如 28 天抗压强度、吸水率或孔隙率；
- **控制变量**：配比、发泡剂、含水状态、成型方式、养护温度和测试龄期；
- **混杂因素**：可能同时改变自变量和因变量的因素，例如孔径分布、试件尺寸或批次差异。

控制变量不能只写“条件一致”，而应写成可检查的范围、单位和记录方式。对于材料实验，还应明确样品制备顺序、随机化或批次安排、重复数、异常值处理规则和测量不确定度。

### 设计最小判别实验

优先选择能够最大程度区分假设、同时控制成本和风险的方案。实验计划至少应包含：样品梯度、对照组、重复数、测量指标、测量时间点、预期结果分支和下一步决策规则。

以密度和抗压强度为例，可以设置多个密度梯度并保持配比、孔结构目标、含水状态和养护条件可比；同时测量孔结构或含水状态，避免只记录密度和强度两个终点。如果控制孔结构后强度差异消失，该结果就构成对“密度本身主导强度变化”这一解释的反例，而不是简单判定实验失败。

### 导入数据并形成下一轮判断

实验结束后按以下顺序处理结果：

1. 上传 CSV 或 XLSX，检查字段名称、单位、样品标识和缺失值。
2. 确认导入，保留一个不可变的数据版本；后续修订应产生新版本，不覆盖旧数据。
3. 先做单列摘要，再按研究问题选择相关性或分组均值；相关性只描述变量关系，不自动证明因果。
4. 查看分析结果对应的源行、源列和数据版本，确认结果没有脱离原始样品记录。
5. 将结果与各假设的预测逐项比较，记录支持、冲突、未决问题和下一步行动。
6. 让课题组成员重新质询解释，并由 PI 决定是否批准阶段性结论或继续补充实验。

## 主要产品能力

### 课题组工作台

课题组是研究上下文的容器，统一承载成员、聊天消息、资料、任务、运行记录、候选结果、组会安排和研究 Memory。

### 多角色 Agent 协作

Agent 具有清晰的角色、能力和数据权限。不同成员可以从不同专业角度独立分析同一个问题，避免所有观点都来自同一种提示和同一种思路。

### Live 研究聊天

聊天是产品的主要入口。用户消息、附件、澄清问题、分析进度和候选审阅都在同一条研究对话中呈现；成员、产物和聊天记录通过覆盖式面板查看，不打断主工作流。

### 受控资料检索

研究任务只检索被授权的课题组资料，并返回带有文档、位置和片段标识的来源。资料可以处于真实、脱敏真实、公开来源或合成数据空间，系统不会混淆不同可信等级。

### 实验数据工作区

支持 CSV/XLSX 数据预览、导入、不可变版本、样品和单位校验，以及摘要、相关性和分组均值等受控分析。分析结果带有数据集版本和源行列引用，默认不把相关性解释为因果关系。

### 候选 Claim 审阅

AI 生成的内容先停留在候选状态，必须经过来源引用校验和用户批准，才会成为正式 Claim。拒绝的候选不会被写成正式结论；批准也不等同于证据已经完成科学验证。

### 组会与 PI 决策

组会围绕竞争性假设、证据链、攻击与回应、未决分歧和待决事项展开。PI 可以追问、补充约束、要求成员回应，并对下一步研究路线作出决定。

### 可追溯科研 Memory

Memory 以追加方式保存判断变化，不覆盖旧版本。研究者可以查看时间线、版本关系和证据关联，理解“我们为什么改变了看法”。

## 首个材料科研场景

ForumMind 以“废弃泥浆基泡沫混凝土”的机理、性能与制备链条作为首个深度场景，关注泥浆掺量、泡沫稳定性、孔结构、密度和强度等变量之间的关系。

这个场景用于展示通用科研协作方法：从模糊问题开始，经过资料检索、竞争性假设、反例质询和判别实验，逐步形成有边界的阶段性认识。产品不是单点失败归因工具，也不会替研究者完成材料制备、养护、测试或表征。

## 可信边界

- AI 输出是可审查的候选解释、资料整理、质疑和实验建议，不是自动生成的最终科学结论。
- 未能定位到来源的内容只能作为线索，不能直接进入正式证据链。
- 相关性、模型判断和一次实验结果不会自动升级为因果结论。
- 真实实验、设备操作、样品制备、测试表征和重大资源投入由研究者或获授权人员负责。
- PI 保留对研究路线、实验条件和正式结论的最终决定权。
- 失败路线、反例、退回理由和被拒绝的候选会被保留，避免研究历史被静默覆盖。

## 产品产出

一次完整的研究协作可以沉淀为：

- 结构化研究问题和任务范围；
- 具备来源、适用边界和不确定性的候选假设；
- Agent 之间的质询、回应和审查意见；
- 可执行的最小判别实验建议；
- 带版本、来源和审批状态的实验分析结果；
- PI 决策、行动项和阶段性结论；
- 能够解释结论如何变化的科研 Memory。

ForumMind 的目标不是替研究者做出所有判断，而是让研究者始终看得见证据、听得到反对意见，并能回到每一次科研决策发生的现场。
